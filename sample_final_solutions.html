I.1

Prove or Disprove

Four claims about Θ, Ω, and how they interact with addition. Two are true by short direct arguments; two fail to counterexamples built from functions of clearly different growth rates.

a f(n) = Θ(g(n)) ⟹ g(n) = Ω(f(n)) PROVE ▸

f(n) = Θ(g(n)) means there are constants \(c_1,c_2>0\) and \(n_0\) such that for all \(n\ge n_0\):

\(c_1\,g(n) \le f(n) \le c_2\,g(n)\)

Take the right-hand inequality, \(f(n)\le c_2 g(n)\), and divide by \(c_2\): \(g(n) \ge \frac{1}{c_2}f(n)\). That is exactly the definition of \(g(n)=\Omega(f(n))\) with constant \(\frac{1}{c_2}\). So Θ is symmetric in a stronger sense than it first looks — bounding \(f\) between multiples of \(g\) automatically bounds \(g\) below by a multiple of \(f\).

b f(n)+g(n) = Θ(min(f(n),g(n))), f,g ≥ 0 DISPROVE ▸
Counterexample

Let \(f(n)=n\) and \(g(n)=n^2\). Then \(\min(f(n),g(n))=n\), while \(f(n)+g(n)=n+n^2=\Theta(n^2)\). Since \(n = o(n^2)\), the sum is not bounded below by any constant multiple of \(\min(f,g)=n\) — the ratio \(\frac{n+n^2}{n}=1+n\) grows without bound instead of staying between two constants.

The identity that is true here (and is easy to confuse this with) is f(n)+g(n) = Θ(max(f(n),g(n))): the larger of the two terms always dominates the sum, but the smaller one gives no such guarantee.

c f(n) = Θ(f(n)) PROVE ▸

Θ is reflexive. Pick \(c_1=c_2=1\) and any \(n_0\): trivially \(1\cdot f(n) \le f(n) \le 1\cdot f(n)\) for all \(n\ge n_0\). Every function is tightly bounded by itself.

d f(n) + Ω(f(n)) = Θ(f(n)) DISPROVE ▸

"\(\Omega(f(n))\)" inside the sum stands for any function that is bounded below by a multiple of \(f(n)\) — it carries no upper-bound guarantee at all. So the claim is really: for every \(h(n)=\Omega(f(n))\), is \(f(n)+h(n)=\Theta(f(n))\)?

Counterexample

Let \(f(n)=n\) and \(h(n)=n^2\). Certainly \(h(n)=\Omega(n)\) (it grows at least as fast). But \(f(n)+h(n)=n+n^2=\Theta(n^2)\), which is not \(\Theta(n)\) — it's strictly larger order. Ω only promises a floor, so the sum can blow past \(\Theta(f(n))\) as far as the chosen \(h\) allows.

II.2

Recurrence — Shifted Two-Way Split

II.2 T(n) = T(n/2 − 1) + T(n/2 − 3) + Dn n log n ▸
\[ T(n) = \begin{cases} T\!\left(\dfrac{n}{2}-1\right) + T\!\left(\dfrac{n}{2}-3\right) + Dn & n>1 \\ C & n=1 \end{cases} \]

Both recursive calls split the problem into (approximately) two halves; the "−1" and "−3" are lower-order shifts that don't change which asymptotic bucket the recurrence falls into — they only shift the recursion tree's boundary by a constant number of elements per level, never the branching factor or the per-level work.

Treating this as \(T(n)\approx 2T(n/2)+\Theta(n)\) — the same shape as Merge Sort's recurrence — a recursion-tree argument confirms it: each of the \(\lg n\) levels does \(\Theta(n)\) total work (the constant shifts only shave a lower-order amount off the subproblem sizes, not the total count of leaves or the per-level sum), giving the classic Master Theorem Case 2 result.

Solution
T(n) = Θ(n·lg n)
II.3

Recurrence — Master Theorem, Case 3

II.3 T(n) = 9T(n/7 − 3) + Dn·∛n MASTER, CASE 3 ▸
\[ T(n) = \begin{cases} 9T\!\left(\dfrac{n}{7}-3\right) + D\,n\sqrt[3]{n} & n>1 \\ C & n=1 \end{cases} \]

Note \(D\,n\cdot n^{1/3} = D\,n^{4/3}\), so \(a=9\), \(b=7\), \(f(n)=\Theta(n^{4/3})\). The "−3" is a lower-order shift and doesn't change \(b\)'s effective value. Compare exponents:

log₇9 ≈ 1.129 < 4/3 ≈ 1.333

So \(f(n)=\Omega\!\left(n^{\log_7 9+\epsilon}\right)\). Check the regularity condition for Case 3, \(a\,f(n/b)\le c\,f(n)\) for some \(c<1\):

9·(n/7)^(4/3) = (9/7^(4/3))·n^(4/3) ≈ 0.67·n^(4/3)

Since \(0.67<1\), regularity holds, and Case 3 applies: the work at the root dominates the whole recursion tree.

Solution
T(n) = Θ(n^(4/3))
II.4

Recurrence — Subtract-and-Conquer

II.4 T(n) = T(n − 3) + Dn UNROLL, n² ▸
\[ T(n) = \begin{cases} T(n-3) + Dn & n>1 \\ C & n=1 \end{cases} \]

This is a subtract-by-constant recurrence, not divide-and-conquer, so the Master Theorem doesn't apply — unroll it directly. There are roughly \(n/3\) levels of recursion before reaching the base case, and the work at each level decreases by 3 each time:

\[ T(n) = C + D\Big(n + (n-3) + (n-6) + \cdots \Big) \]

This is an arithmetic series of about \(n/3\) terms, averaging roughly \(n/2\) each, so the sum is \(\approx \dfrac{n}{3}\cdot\dfrac{n}{2} = \dfrac{n^2}{6}\) — the same shape as \(T(n)=T(n-1)+\Theta(n)\), the standard "insertion-sort-style" linear recursion.

Solution
T(n) = Θ(n²)
III

Hire-Assistant: Probability of Exactly k Hires

In Hire-Assistant, you hire a new assistant every time the current candidate beats every candidate interviewed so far. "Hiring exactly k times out of n" is exactly the event that the random permutation of candidates has exactly k left-to-right maxima (records) — counted by the unsigned Stirling numbers of the first kind, ⌊n, k⌋.

III n = 8 candidates, all orders equally likely STIRLING (1ˢᵗ KIND) ▸

For \(n\) candidates, the number of orderings that produce exactly \(k\) hires equals \(\left[{n\atop k}\right]\), the unsigned Stirling number of the first kind — the count of permutations of \(n\) elements with exactly \(k\) left-to-right maxima. Two endpoints are easy to reason about directly, and the middle two come from the recurrence \(\left[{n\atop k}\right] = \left[{n-1\atop k-1}\right] + (n-1)\left[{n-1\atop k}\right]\):

  • Exactly 8 hires — every candidate must beat all before them, i.e. the order is fully increasing. Only 1 such permutation exists.
  • Exactly 1 hire — only the very first candidate hired, meaning the overall best candidate must appear first; the other 7 can follow in any order: \(7! = 5040\) permutations.
  • Exactly 7 hires — all but one candidate is a "record." This happens precisely when the permutation is one transposition away from fully increasing, i.e. \(\binom{8}{2}=28\) permutations.
  • Exactly 2 hires — from the recurrence table for row \(n=8\): \(\left[{8\atop 2}\right] = 13068\).

(As a check, the full row for \(n=8\), \(k=1\ldots8\), is \(5040,\,13068,\,13132,\,6769,\,1960,\,322,\,28,\,1\) — and it sums to \(8! = 40320\), as it must, since every permutation has some well-defined number of records.)

IV.1

MaxHeapify Precondition

1 Effect of MaxHeapify(A, i) when i < heap-size/2 DESIGN NOTE ▸

MaxHeapify assumes the subtrees rooted at LEFT(i) and RIGHT(i) are already valid max-heaps, but that A[i] itself might violate the heap property against its children. Because i < A.heap-size/2, node i is guaranteed to be an internal node (leaves live at indices > ⌊heap-size/2⌋), so it has at least one real child to compare against.

The call lets the value at A[i] "float down" — repeatedly swapping with its larger child — until it either reaches a position where it's ≥ both children, or falls all the way to a leaf. The net effect: the subtree rooted at i becomes a valid max-heap.

IV.2

Reversing the BuildMaxHeap Loop

2 for i = 1 to ⌊A.length/2⌋ instead of downto WOULD NOT WORK ▸

No — running the loop upward from the root toward the middle breaks MaxHeapify's precondition. MaxHeapify(A, i) only works correctly if the subtrees at LEFT(i) and RIGHT(i) are already max-heaps. The original loop runs from ⌊n/2⌋ downto 1 — bottom-up — so every child subtree is heapified before its parent is processed.

Reversing the direction would call MaxHeapify(A, 1) — the root — first, while its children's subtrees are still unheapified garbage. The sift-down at the root would use incorrect information about its children and could place the wrong element there; later calls further down wouldn't fix that mistake, since MaxHeapify never revisits ancestors. The result is not guaranteed to be a max-heap.

IV.3

Heapsort on Already-Sorted Input

3–4 Increasing-order input, and decreasing-order input Θ(n lg n), BOTH ▸

BuildMaxHeap runs in \(\Theta(n)\) regardless of the input's initial order — that bound comes from summing heap heights across levels, an aggregate argument that doesn't depend on which permutation of values is being heapified. After that, Heapsort repeatedly extracts the max and re-heapifies, and each of the \(n-1\) extractions costs \(\Theta(\lg n)\) in the worst case for any array of that size, sorted or not — Heapsort has no shortcut path for inputs that happen to already be ordered.

So whether A starts sorted ascending or descending, the total cost is the same:

Sorted increasing
Θ(n lg n)
Sorted decreasing
Θ(n lg n)
IV.4

Best-Case Running Time of Heapsort

5 Best case over all inputs of size n Θ(n lg n) ▸

Unlike, say, Insertion Sort (which has an \(O(n)\) best case on already-sorted input), Heapsort's structure — build a heap, then repeatedly swap the max to the end and sift down — doesn't have an input arrangement that meaningfully shortens the work. Building the heap always costs \(\Theta(n)\), and the \(n-1\) extract-and-sift steps always cost \(\Theta(\lg n)\) each on average across the run. So the best, average, and worst cases all coincide at:

Θ(n lg n)

V.1

Partition / Quicksort on All-Equal Input

1–2 A[p..r] all equal — what q, and what running time? q = r, Θ(n²) ▸ 
Partition(A, p, r){
  x = A[r];
  i = p - 1;
  for(j = p to r-1){
    if(A[j] <= x){        // always true — every element equals x
      i = i + 1;
      exchange A[i] with A[j]
    }
  }
  exchange A[i+1] with A[r];
  return i+1;
}

Since every element equals the pivot x = A[r], the test A[j] <= x is true on every iteration, so i increments every time and ends the loop at i = r-1. The final swap exchanges A[r] with itself (a no-op), and the function returns:

q = r

Because q always lands at the very end of the subarray, every recursive call is QuickSort(A, p, r-1) paired with an empty QuickSort(A, r+1, r) — the most unbalanced split possible (sizes \(n-1\) and \(0\)), identical in shape to sorting an already-sorted array. That gives the worst-case recurrence \(T(n)=T(n-1)+\Theta(n)\):

Θ(n²)
V.2

Partition / Quicksort on Already-Sorted Input

3–4 A[p..r] already sorted ascending — what q, and what running time? q = r, Θ(n²) ▸

When A is sorted ascending, the pivot x = A[r] is the maximum element of the subarray, so A[j] <= x holds for every j from p to r-1 — exactly the same trace as the all-equal case above. i increments on every iteration, ending at r-1, and the final swap is a no-op.

q = r

Again the pivot always lands at the last position, giving the maximally unbalanced \((n-1, 0)\) split at every level of recursion — this is precisely Quicksort's textbook worst case.

Θ(n²)
V.3

Fixing Quicksort's Worst Case

5 How to avoid the Θ(n²) worst case in practice DESIGN ▸

The two traces above show the problem: always picking A[r] as the pivot is a fixed, predictable rule, so any adversary (or unlucky input, like a sorted or all-equal array) can force the worst-case split every single time.

The standard fix is randomization: before partitioning, swap A[r] with a uniformly random element of A[p..r] (Randomized-Partition). No fixed input can force bad behavior anymore, because the pivot choice no longer depends on the input's order — it depends on a fresh random draw each call. This gives an expected running time of \(\Theta(n\lg n)\) for any input, with the \(\Theta(n^2)\) case becoming vanishingly unlikely rather than guaranteed.

A related deterministic alternative is median-of-three (or, for a hard worst-case guarantee, the median-of-medians linear-time selection algorithm) to pick a pivot that's provably close to the true median, bounding the split ratio away from the degenerate \((n-1,0)\) case.

VI.2

Running the Final Loop Forward Instead of Backward

2 Line 8: "for j = 1 to A.length" instead of downto — still correct? YES — but not stable ▸

Answer: Yes, the array would still come out fully sorted.

Correctness of CountingSort depends only on the cumulative array C, which tells you the contiguous block of output positions reserved for each value — it says nothing about the order in which equal-valued elements fill that block. Iterating j forward instead of backward still places every occurrence of a value \(v\) somewhere inside \(v\)'s correct block; it just changes which copy of a repeated value lands in which slot within that block.

What breaks is stability: the standard backward loop preserves the original relative order of equal elements (the one that appeared earlier in A also appears earlier in B). Running forward reverses that relative order among ties, since the last-seen copy of a value now claims the highest remaining slot in its block first. The output is still a valid sorted array — just not a stable sort anymore.

VI.3

Design: Sorting n/k Pre-Blocked Subsequences in O(n log k)

3 Blocks already in relative order — sort each block internally DESIGN ▸

The setup guarantees the \(n/k\) blocks are already correctly ordered relative to each other — every element in block \(i\) is smaller than every element in block \(i+1\). The only disorder is within each block of \(k\) elements. So no merging across blocks is needed at all: sort each block on its own, then concatenate the blocks in their existing order.

SORT-BLOCKS(A, n, k):
1  for i = 0 to n/k - 1:
2      let block = A[i·k + 1 .. i·k + k]        // the i-th group of k elements
3      Merge-Sort(block)                         // or Heapsort — any Θ(k lg k) sort
4      write block back into A[i·k + 1 .. i·k + k]
5  return A                                       // blocks are already in order — done
Running time

Each of the \(n/k\) blocks is sorted independently in \(\Theta(k\lg k)\) time using any comparison-based sort:

(n/k) · Θ(k lg k) = Θ(n lg k)
