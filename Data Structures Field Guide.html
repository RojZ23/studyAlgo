    01 / Hash Tables

    Hash Tables

    A generalization of an array: instead of indexing directly by key, compute a function of the key — a hash function — and index by that. Trades guaranteed O(1) direct addressing for O(1) expected time using far less space.

    Direct Addressing baseline

    Array T indexed directly by key: T[k] = x. O(1) per operation, but needs one slot per possible key in the universe U.

    Load Factor

    α = n / m — n = elements stored, m = table size (number of slots / linked lists). Drives every average-case bound below.

    Good Hash Function

    Satisfies simple uniform hashing: each key equally likely to hash to any of the m slots, independent of other keys.

    Running Times

    MethodSearch (avg)Search (worst)InsertDelete
    ChainingΘ(1 + α)Θ(n)O(1)O(1)†
    Open addressing≤ 1/(1−α)Θ(n)≤ 1/(1−α)—‡

    † O(1) worst-case with doubly linked lists. ‡ Open addressing needs a DELETED sentinel, not plain NIL, or probe sequences break.

    Hash Functions

    • Division: h(k) = k mod m. Pick m prime, not close to a power of 2.
    • Multiplication: h(k) = ⌊m(kA mod 1)⌋, 0 < A < 1. m's exact value doesn't matter; Knuth suggests A ≈ (√5−1)/2.
    • Universal: hab(k) = ((ak+b) mod p) mod m, p prime > all keys and > m. Pick a,b randomly each run → defeats adversarial key sets.

    Collision Resolution

    • Chaining: each slot is a linked list of colliding elements.
    • Linear probing: h(k,i) = (h'(k)+i) mod m. Suffers primary clustering.
    • Quadratic probing: h(k,i) = (h'(k)+c1i+c2i²) mod m. Suffers secondary clustering.
    • Double hashing: h(k,i) = (h1(k)+i·h2(k)) mod m, h2(k) must be relatively prime to m.

    Perfect Hashing

    Two-level scheme giving O(1) worst-case search on a static key set: level 1 is ordinary universal hashing with chaining into secondary tables Sj; level 2 sizes each Sj to (number of keys in it)² and rehashes with a fresh universal function until zero collisions occur inside it. Expected number of collisions across the whole structure is < ½, so a collision-free level-2 function is found quickly.

    Why not just direct-address?

    Direct addressing needs an array sized to the whole key universe U. When the number of keys actually in use, n, is much smaller than |U| — or the keys aren't small integers at all — allocating |U| slots wastes space or is outright impossible. A hash table instead uses Θ(n) space: an array sized proportional to the number of keys you expect to store, plus a hash function h: U → {0, ..., m−1} that maps each key down into that smaller range.

    The cost of shrinking the index space is that two distinct keys can land on the same slot — a collision. Every hash table design is really a design choice about (1) what hash function to use and (2) how to resolve collisions.

    Chaining — analysis

    Under simple uniform hashing, the expected length of any chain is the load factor α = n/m. An unsuccessful search examines an average of α elements before hitting the end of a list (expected Θ(1+α) counting the O(1) to compute h(k)). A successful search is essentially the same, since it's symmetric with insertion order — also Θ(1+α).

    If the table is built so that n = O(m), then α = O(1), and every dictionary operation runs in O(1) time on average.

    Hash functions — design notes

    Division method: fast (one mod operation) but sensitive to the choice of m. Avoid m = 2p (h(k) then just extracts the low p bits of k and ignores the rest — bad if keys aren't uniformly random in those bits). A prime not close to a power of 2 is the safe default.

    Multiplication method: value of m is not critical (a power of 2 is fine and fast to implement). Multiply key k by a constant A ∈ (0,1), take the fractional part, scale by m, floor it. Slower than division in practice but more forgiving.

    Random / universal hashing: defends against an adversary who knows your hash function in advance and chooses keys to force worst-case collisions. Instead of a single fixed function, pick one at random, independently of the keys, from a carefully designed family H. A family is universal if for any two distinct keys k ≠ l, the number of h ∈ H with h(k) = h(l) is at most |H|/m — i.e. the collision probability for any fixed pair is at most 1/m, exactly what you'd get from a truly random function.

    Open addressing — mechanics

    No pointers: every element lives inside the table itself, so the table can fill up (α ≤ 1 always). To insert key k, probe slots in the sequence h(k,0), h(k,1), ..., h(k,m−1) — a permutation of {0,...,m−1} — until an empty slot is found. Searching follows the identical sequence, stopping either at a slot holding k (success) or the first empty slot (failure, since if k had been inserted it would have stopped there too).

    Deletion is the tricky part. You cannot just write NIL into a deleted slot — a later search for a different key k′ that originally probed through k's slot during insertion would incorrectly stop early and report "not found." Fix: mark the slot with a special DELETED value. Search treats DELETED as occupied (keep probing past it); insertion treats DELETED as empty (reusable).

    Practical considerations

    On real hardware, memory hierarchy matters: caches are small and fast, and a cache line (e.g. 64 contiguous bytes) is much cheaper to keep reusing than to re-fetch from main memory. Linear probing looks worse than double hashing in the pure RAM cost model, but its successive probes usually land in the same cache line, so it can outperform double hashing in practice.

    Multiplication method, worked

    k = 123456, m = 214, A = (√5−1)/2 style constant ≈ 2,654,435,769 / 232.

    h(123456) = floor( 2^14 * (123456 * 2,654,435,769 / 2^32  mod 1) )
          = floor( 2^14 * (17,612,864 / 2^32) )
          = floor( 2^14 * 0.004100814 )
          = floor( 67.18774 )
          = 67

    Second worked case, k = 123456, m = 10,000, A = (√5−1)/2:

    h(123456) = floor( 10000 * (123456 * A mod 1) )
          = floor( 10000 * 0.0041151... )
          = floor( 41.151 )
          = 41

    Universal hashing, worked

    Family Hpm: hab(k) = ((ak + b) mod p) mod m. Take p = 17, m = 6, a = 3, b = 4, k = 8:

    h(3,4)(8) = ((3*8 + 4) mod 17) mod 6
          = (28 mod 17) mod 6
          = 11 mod 6
          = 5

    Double hashing, worked

    Table size m = 13. h1(k) = k mod 13, h2(k) = 1 + (k mod 11). Insert k = 14:

    h1(14) = 14 mod 13 = 1
h2(14) = 1 + (14 mod 11) = 1 + 3 = 4

probe sequence: 1, 5, 9, 0, 4, 8, ...  (i.e. 1, 1+4, 1+8, 1+12 mod 13, ...)

    We probe slot 1 first; if occupied, slot (1+4) mod 13 = 5; then (1+8) mod 13 = 9; and so on, stepping by h2(k) = 4 each time.

    Perfect hashing — collision expectation

    With n keys hashed into a table of size n², the probability any given pair collides is 1/n². Let X count collisions over all C(n,2) pairs:

    E[X] = C(n,2) * 1/n^2
     = [n(n-1)/2] * 1/n^2
     = (n-1)/(2n)
     < 1/2

    Expected collisions are under ½ — so a random function from a universal family has better-than-even odds of producing zero collisions on the first try, and repeated tries converge fast.

    PROBLEM 2Core

    Table size m = 13, linear probing with h'(k) = k mod 13. Insert 18, 26, 5, 44, 31 in order. Give the final slot of each key.

    h1(25) = 25 mod 13 = 12.

    h2(25) = 1 + (25 mod 11) = 1 + 3 = 4.

    Probe sequence: i=0 → 12; i=1 → (12+4) mod 13 = 3; i=2 → (12+8) mod 13 = 7.

    First three probes: 12, 3, 7.

    PROBLEM 4Conceptual

    A table has load factor α = 0.9 under open addressing with uniform hashing. About how many probes does an unsuccessful search take? What about α = 0.5? What does this tell you about keeping open-addressed tables sparse?

    Expected probes for an unsuccessful search ≤ 1/(1−α).

    α = 0.9 → 1/(1−0.9) = 1/0.1 = 10 probes.

    α = 0.5 → 1/(1−0.5) = 2 probes.

    Growth is not linear in α — it blows up as α → 1. Open-addressed tables should typically be resized well before they get close to full (commonly around α ≈ 0.7–0.75) to keep probe counts small.

    PROBLEM 5Challenge

    Explain why h2(k) in double hashing must be relatively prime to the table size m (e.g. why choosing m a power of 2 and h2(k) always even is dangerous).

    The probe sequence is (h1(k) + i·h2(k)) mod m for i = 0..m−1. This sequence visits every slot 0..m−1 exactly once only if gcd(h2(k), m) = 1 — i.e. h2(k) generates the full cyclic group mod m.

    If gcd(h2(k), m) = d > 1, the probe sequence only ever visits m/d distinct slots (a coset), no matter how many times you probe. E.g. m = 16 and h2(k) always even means only 8 of the 16 slots are ever reachable — insertion can fail with "table full" even when half the table is empty.

    Common fixes: choose m prime and let h2(k) return a value in [1, m−1], or force h2(k) to always be odd when m is a power of 2.

    02 / Binary Search Trees

    Binary Search Trees

    A linked structure where every node satisfies the binary-search-tree property: everything in the left subtree is ≤ the node's key, everything in the right subtree is ≥ it. Every operation below runs in O(h), h = tree height.

    BST Property

    For node x: if y is in x's left subtree, key[y] ≤ key[x]. If y is in x's right subtree, key[y] ≥ key[x].

    Operations — all O(h)

    OperationIdea
    SEARCH(x,k)Compare k to key[x]; recurse left if k<key[x], right if k>key[x], return x if equal.
    MINIMUM(x)Follow left pointers until NIL.
    MAXIMUM(x)Follow right pointers until NIL.
    SUCCESSOR(x)If right subtree exists: MINIMUM(right[x]). Else: walk up while x is a right child.
    PREDECESSOR(x)Mirror image of successor (left subtree / walk up while a left child).
    INSERT(T,z)Walk down from root comparing keys; hang z off the NIL you fall off of.
    DELETE(T,z)3 cases — see Notes. Uses TRANSPLANT as a subroutine.

    Tree Walks — all Θ(n)

    Inorder
    left, root, right
    Visits keys in sorted order.
    Preorder
    root, left, right
    Root printed first.
    Postorder
    left, right, root
    Root printed last.
    On a tree built from n random insertions the expected height is O(lg n), giving O(lg n) expected operations — but a degenerate insertion order (e.g. sorted input) produces a linked-list-shaped tree with height Θ(n). This worst case is exactly what red-black trees fix.

    Search

    TREE-SEARCH(x, k)
1  if x == NIL or k == key[x]
2      then return x
3  if k < key[x]
4      then return TREE-SEARCH(left[x], k)
5      else return TREE-SEARCH(right[x], k)

    Running time O(h). An iterative version unrolls the recursion into a while loop and typically runs faster in practice on most machines (no call-stack overhead).

    Minimum / Maximum

    TREE-MINIMUM(x)
1  while left[x] != NIL
2      do x ← left[x]
3  return x

TREE-MAXIMUM(x)
1  while right[x] != NIL
2      do x ← right[x]
3  return x

    Successor & Predecessor

    successor(x) = node y with the smallest key > key[x].

    • Case 1: right[x] is non-empty → successor is TREE-MINIMUM(right[x]).
    • Case 2: right[x] is empty → go up until you move up from a left child; that parent is the successor. (If you reach the root without ever being a left child, x was the maximum — no successor.)
    TREE-SUCCESSOR(x)
1  if right[x] != NIL
2      then return TREE-MINIMUM(right[x])
3  y ← p[x]
4  while y != NIL and x == right[y]
5      do x ← y
6         y ← p[y]
7  return y

    Predecessor is the exact mirror: left subtree's maximum, or walk up while x is a left child.

    Insertion

    Trace a path down from the root, going left or right by comparing the new value against each node's key, until falling off the tree (hitting NIL). Track a trailing pointer y to the last non-NIL node visited — that becomes the new node's parent.

    TREE-INSERT(T, z)
1  y ← NIL
2  x ← root[T]
3  while x != NIL
4      do y ← x
5         if key[z] < key[x]
6             then x ← left[x]
7             else x ← right[x]
8  p[z] ← y
9  if y == NIL
10     then root[T] ← z           // tree T was empty
11     elseif key[z] < key[y]
12         then left[y] ← z
13         else right[y] ← z

    Deletion — three cases

    1. z has no children: just remove it (splice out).
    2. z has exactly one child: splice z out, linking that child directly to z's parent.
    3. z has two children: find z's successor y (which must be TREE-MINIMUM of z's right subtree, so y has no left child). Either y is z's right child (replace z by y directly), or y is deeper (replace y in its own position by y's right child, then move y into z's position with both of z's children).

    CLRS implements this cleanly with a TRANSPLANT helper that replaces the subtree rooted at u with the subtree rooted at v (rewiring u's parent to point at v):

    TRANSPLANT(T, u, v)
1  if p[u] == NIL
2      then root[T] ← v
3  elseif u == left[p[u]]
4      then left[p[u]] ← v
5      else right[p[u]] ← v
6  if v != NIL
7      then p[v] ← p[u]
    TREE-DELETE(T, z)
1  if left[z] == NIL
2      then TRANSPLANT(T, z, right[z])          // no left child
3  elseif right[z] == NIL
4      then TRANSPLANT(T, z, left[z])           // no right child
5  else y ← TREE-MINIMUM(right[z])           // y = successor
6      if p[y] != z
7          then TRANSPLANT(T, y, right[y])
8               right[y] ← right[z]
9               p[right[y]] ← y
10     TRANSPLANT(T, z, y)
11     left[y] ← left[z]
12     p[left[y]] ← y

    Why height matters

    Every operation above costs O(h). For a random build, h = O(lg n) and everything is fast. But a plain BST gives no guarantee on h — inserting sorted data builds a degenerate chain of height Θ(n), making every operation O(n). Red-black trees (next topic) add a rebalancing rule that guarantees h = O(lg n) always.

    Traversal example

    Given the tree with root 5, left child 3 (children 2, 4), right child 9 (children 7, ...):

              5
        /   \
       3     9
      / \   /
     2   4 7
    WalkOutput
    Inorder2, 3, 4, 5, 7, 9
    Preorder5, 3, 2, 4, 9, 7
    Postorder2, 4, 3, 7, 9, 5

    TREE-SEARCH example

    Tree: root 15, left child 6 (children 3, 7 — 7 has child 13, which has child 9), right child 18 (right child 20). Searching for key 13:

    path: 15 → 6 → 7 → 13   (found)

    At each step: 13 < 15 → go left to 6; 13 > 6 → go right to 7; 13 > 7 → go right to 13; match.

    Successor / predecessor example

    Same tree (root 15, left subtree 6/3/7/13/9-ish, right subtree 18/20):

    • successor(15) = TREE-MINIMUM(right subtree of 15) = 17 (the minimum of the right side).
    • successor(13) = 15 — 13 has no right child, so walk up: 13 is a right child of 7, keep going; 7 is a left child of 6... continue up until the first "left child" turn, landing on 15.
    • predecessor(9) = 7 — 9 has no left child, walk up until finding an ancestor where you moved up from a right child.

    TREE-INSERT example

    Insert value 13 into a tree with root 12: x starts at root, y trails behind. 13 > 12 → move right to 18; y = 12. 13 < 18 → move left to 15; y = 18. 13 < 15 → move left to 9; y = 15. 13 > 9 → move right, hit NIL; y = 9. Loop ends, x = NIL, y = 9. Since 13 > key[9], attach: right[9] = 13.

    PROBLEM 4Conceptual

    Why does TREE-MINIMUM(right[z]) always have no left child when used as a successor during deletion? Why does that matter for correctness of TREE-DELETE?

    TREE-MINIMUM walks left pointers until it hits NIL — by construction the node it returns has left = NIL. That guarantees y (the successor) can be removed from its original spot with the simple one-child-or-no-child TRANSPLANT (line 7: TRANSPLANT(T, y, right[y])) without needing to recursively handle a two-children case for y itself. This is exactly what keeps deletion O(h) instead of needing recursion.

    PROBLEM 5Challenge

    You insert the keys 1, 2, 3, 4, 5, 6, 7 into an empty BST in that order. What is the height of the resulting tree, and what does this imply about worst-case TREE-SEARCH time on it?

    Each new key is larger than everything already in the tree, so every node becomes the right child of the previous one — a straight chain: 1→2→3→4→5→6→7. Height h = n−1 = 6.

    Since every operation is O(h), search/insert/delete on this tree degrade to O(n) — identical to a linked list. This is precisely the worst case a plain BST cannot rule out, motivating balanced trees like red-black trees.

    03 / Red-Black Trees

    Red-Black Trees

    A binary search tree with one extra bit per node (its color) and five invariants that together guarantee height O(lg n) — so search, insert, and delete are all O(lg n) worst-case, no matter the insertion order.

    The 5 Properties

    1. Every node is either red or black.
    2. The root is black.
    3. Every leaf (NIL) is black.
    4. If a node is red, both its children are black. (no two reds in a row)
    5. Every path from a node to its descendant leaves has the same number of black nodes (its black-height).

    Height Bound

    A red-black tree with n internal nodes has height h ≤ 2 lg(n + 1). Property 4 forces at least half the nodes on any root-to-leaf path to be black, so black-height(root) ≥ h/2, giving n ≥ 2h/2 − 1 and the bound above.

    Rotations

    O(1) local restructuring operations that preserve the BST property while changing which node is "on top." LEFT-ROTATE and RIGHT-ROTATE are mirror images. Every fixup is built entirely out of rotations + recolorings.

    Insert / Delete Fixup

    Ordinary BST-insert/delete can violate properties 1–5. RB-INSERT-FIXUP and RB-DELETE-FIXUP walk back up the tree, using the sibling/uncle's color to pick one of a small number of cases, each resolved in O(1) rotations before moving up — O(lg n) total.

    Why not a plain BST?

    Plain BST operations run in O(h), and h can be as bad as Θ(n) for adversarial insertion orders. A red-black tree adds bookkeeping (a color per node) and a rebalancing rule so that h is always O(lg n), guaranteeing O(lg n) worst-case for every dictionary operation.

    RIGHT-ROTATE(T, x)

    Pivots x down and its left child y up, keeping the BST property intact. LEFT-ROTATE is the exact mirror (swap left/right throughout).

    RIGHT-ROTATE(T, x)
1  y ← left[x]
2  left[x] ← right[y]
3  if right[y] != T.nil
4      then p[right[y]] ← x
5  p[y] ← p[x]
6  if p[x] == T.nil
7      then T.root ← y
8  elseif x == right[p[x]]
9      then right[p[x]] ← y
10     else left[p[x]] ← y
11 right[y] ← x
12 p[x] ← y

    RB-INSERT-FIXUP — the idea

    Insert z normally as in a plain BST, color it red (least likely to break the black-height property), then repair. While z's parent is red (property 4 violated), look at z's uncle y = z.p.p.left (or .right, mirrored):

    • Case 1 — uncle y is red: recolor parent and uncle black, grandparent red, move z up to grandparent, keep fixing.
    • Case 2 — uncle y is black, z is a "triangle" (z is a right child, parent is a left child): rotate to turn it into a "line" (Case 3).
    • Case 3 — uncle y is black, z is a "line": recolor parent black / grandparent red, then rotate the grandparent. Done — loop terminates.
    RB-INSERT-FIXUP(T, z)
16  y ← z.p.p.left
17  if y.color == RED
18      z.p.color ← BLACK
19      y.color ← BLACK
20      z.p.p.color ← RED
21      z ← z.p.p
22  else
23      if z == z.p.left
24          z ← z.p
25          RIGHT-ROTATE(T, z)
26      z.p.color ← BLACK
27      z.p.p.color ← RED
28      LEFT-ROTATE(T, z.p.p)
29  T.root.color ← BLACK

    (Shown for the case where z's parent is a left child of the grandparent; the mirror case swaps left/right throughout. Line 29 always re-blackens the root in case it turned red.)

    Cost

    Each RB-INSERT-FIXUP loop iteration is O(1). Case 1 is the only one that continues the loop (moving z two levels up), so the loop runs O(lg n) times total; Cases 2–3 do at most one rotation and terminate. Overall insertion is O(lg n). Deletion follows the same shape — O(lg n) with more cases (an extra "doubly-black" concept) but the same O(lg n) bound.

    Height bound, worked

    For n = 1,000,000 internal nodes: h ≤ 2 lg(1,000,001) ≈ 2 × 19.93 ≈ 39.9. So no matter how those million keys were inserted, the tree never gets taller than about 40 — compare to a degenerate BST, which could be a million deep.

    Case 1 walk-through (recoloring only)

    Insert z as a red left-left grandchild where z's uncle is red. Fixup recolors z's parent and uncle black, grandparent red, then continues the loop with z re-pointed at the grandparent — possibly triggering another fixup iteration further up if the grandparent's parent is also red. No rotation happens in this case; it's pure recoloring, which is why it's the only case that needs to keep looping.

    Case 2 → Case 3 walk-through

    z is a red right child whose parent is a red left child (a "triangle" shape) and the uncle is black. Case 2 applies a rotation at the parent to turn the triangle into a straight "line" (z becomes the left child of its former parent, which is now z's child) — this doesn't fix the violation by itself, it just falls through into Case 3, which recolors and rotates at the grandparent to finish.

    PROBLEM 1Warm-up

    Which of the 5 red-black properties is violated immediately after a plain BST-insert colors the new node red, if its parent happens to also be red? Which property is never at risk from a plain insertion?

    Violated: Property 4 (a red node with a red child/parent — two reds in a row).

    Never at risk: Property 5 (black-heights) — inserting a red node adds zero black nodes to any path, so every path's black-node count is unchanged. This is exactly why insertion colors the new node red rather than black: coloring it black would immediately break property 5 on every path through it.

    PROBLEM 2Core

    A red-black tree has n = 63 internal nodes. What's the maximum possible height? What's the minimum possible height (i.e. if it were a perfectly balanced binary tree)?

    Max height: h ≤ 2 lg(63+1) = 2 lg(64) = 2 × 6 = 12.

    Min height: a perfectly balanced tree with 63 = 26−1 nodes has height lg(64) − 1 = 5 (levels 0 through 5, fully packed).

    PROBLEM 3Core

    During RB-INSERT-FIXUP, z's uncle is red. What does the algorithm do, and why does it need to keep looping afterward (unlike Cases 2/3)?

    Case 1: recolor z's parent black, z's uncle black, and z's grandparent red. Then set z ← z.p.p (grandparent) and re-check the loop condition.

    It must keep looping because recoloring the grandparent red might create a new red-red violation one level further up (between the grandparent and its parent) — the violation has effectively moved two levels up the tree rather than being resolved. Cases 2 and 3 instead end with a rotation that leaves the subtree's root black, which can never conflict with the node's own parent, so they always terminate the loop.

    PROBLEM 4Conceptual

    Why is RB-INSERT-FIXUP's loop guaranteed to run O(lg n) times rather than O(n) times?

    The only case that continues the loop (Case 1) moves the "current node" z two levels up the tree each iteration (to z.p.p). Since the tree has height O(lg n) (that's the whole point of a red-black tree), you can move up at most O(lg n) times before hitting the root. Cases 2 and 3 always terminate immediately after one rotation, so they can't blow up the iteration count either.

    PROBLEM 5Challenge

    Sketch why a single RIGHT-ROTATE or LEFT-ROTATE never breaks the underlying binary-search-tree property, even though it changes the shape of the tree.

    RIGHT-ROTATE(T, x) with y = left[x] only rearranges x, y, and y's right subtree — call it β. Before rotation: β is between y and x in key order (y ≤ β ≤ x, since β = right[y] which is > y but still < x as it's in x's left subtree). After rotation, β becomes x's left subtree, and x becomes y's right child. That ordering (y ≤ β ≤ x) is exactly what's required for β to sit as x's left child while x sits as y's right child — the relative order of every key is preserved, only the pointer structure changes. Everything outside {x, y, β} is untouched.

    04 / B-Trees

    B-Trees

    A balanced multiway search tree designed around disk I/O, not comparisons: each node is sized to fill one disk page, so a node holds many keys and children, keeping the tree shallow and minimizing expensive disk reads.

    Why B-Trees exist

    Disk seek/rotation time is milliseconds (10−3s); main-memory access is nanoseconds (10−9s) — a 5–6 order-of-magnitude gap. Once the read/write head is positioned, streaming data is comparatively cheap. So the goal is to minimize the number of disk pages touched, even if that means more work per page. A B-tree node is sized to exactly one disk page, making the branching factor huge and the tree very shallow.

    Properties (minimum degree t ≥ 2)

    # of keys# of children
    Min (non-root)t − 1t
    Max2t − 1 (node is "full")2t

    The root is exempt from the minimum — it may have as few as 1 key (and 2 children), or even 0 keys if the whole tree is empty.

    Node attributes

    • x.n — number of keys currently in x
    • x.key1..n — keys in nondecreasing order
    • x.leaf — boolean, true if x is a leaf
    • x.c1..n+1 — child pointers (internal nodes only)

    Height & running time

    Height is O(logt n) — dramatically shallower than a binary tree for large t. Search/insert/delete all touch O(h) = O(logt n) nodes, i.e. O(logt n) disk accesses, each doing O(t) in-memory work to scan the node — total O(t logt n) time.

    Formal properties (CLRS)

    1. Every node x has: x.n (# keys), the keys themselves x.key1 ≤ ... ≤ x.keyx.n, and x.leaf.
    2. Each internal node also has x.n + 1 children pointers x.c1, ..., x.cx.n+1. Leaves have none.
    3. The keys x.keyi separate the ranges of keys in each subtree: if ki is any key in the subtree rooted at x.ci, then k1 ≤ x.key1 ≤ k2 ≤ x.key2 ≤ ... ≤ x.keyx.n ≤ kx.n+1.
    4. All leaves have the same depth — the tree's height h. This is what keeps B-trees balanced.
    5. Nodes have lower/upper bounds on key count, governed by the minimum degree t ≥ 2: every node other than the root has at least t−1 keys (at least t children if internal); every node has at most 2t−1 keys (at most 2t children). A node with exactly 2t−1 keys is full.

    The disk-I/O argument

    A B-tree node is deliberately sized to be as large as a whole disk page, which is what limits (and determines) t. Because one node read = one disk access regardless of how many keys are packed into that node, making nodes as large as possible (many keys, high branching factor) directly minimizes the number of disk accesses needed to reach any key — the tree's height shrinks logarithmically in t rather than in 2.

    Insertion (single-pass, split-on-the-way-down)

    Standard B-tree insertion never inserts into a full node directly. Instead, while descending from the root looking for the right leaf, it proactively splits any full node it passes through before recursing into it. Splitting a full node (2t−1 keys) sends its median key up to the parent and divides the remaining 2t−2 keys into two nodes of t−1 keys each — both now valid, and the parent gains one key (never itself becoming over-full because it was already checked/split at this pass). If the root itself is full, a split there is the only way a B-tree's height grows — growth happens at the top, keeping the tree perfectly height-balanced.

    Deletion — the guiding idea

    Symmetric to insertion: never recurse into a node with only the minimum t−1 keys. Before descending into such a child, either borrow a key from an adjacent sibling that has spare keys (a rotation through the parent), or merge the child with a sibling (pulling a key down from the parent) if no sibling has any to spare. This guarantees every node you actually delete from has ≥ t keys, so removing one never underflows it.

    Example tree

    Minimum degree t = 3 (min 2 keys, max 5 keys per node):

                         [ M ]
                    /       \
              [D H]           [Q T X]
             /  |  \          /  |  \  \
          [BC][FG][JKL]  [NP][RS][VW][YZ]

    Root has 1 key (M) and 2 children — fine, since the root is exempt from the minimum-key rule. Every internal node's key count sits within [t−1, 2t−1] = [2,5], and every leaf is at the same depth (2), satisfying property 4.

    Min/max, worked (t = 2)

    # keys# children
    Min (non-root)t − 1 = 1t = 2
    Max2t − 1 = 32t = 4

    With t = 2 a "full" node has 3 keys and 4 children — this specific case (t=2) is often called a 2-3-4 tree in other textbooks.

    PROBLEM 1Warm-up

    For a B-tree with minimum degree t = 4, what is the minimum and maximum number of keys a non-root node can hold? What about the minimum and maximum number of children?

    Keys: min = t−1 = 3, max = 2t−1 = 7.

    Children: min = t = 4, max = 2t = 8.

    PROBLEM 2Core

    A B-tree node x is "full" and you're inserting a new key that would route through x on the way to a leaf. What does the insertion algorithm do to x before continuing down, and why is it done proactively rather than waiting until x actually overflows?

    The algorithm splits x immediately: its median key moves up into x's parent, and the remaining keys divide into two new nodes of t−1 keys each.

    It's done proactively (on the way down, before recursing) so the whole operation stays a single top-to-bottom pass with no backtracking. If you waited until a node actually overflowed (2t keys) after insertion, you'd need to walk back up the tree fixing overflows one level at a time — correct, but requires a second pass. Splitting full nodes pre-emptively guarantees the parent you're about to move into always has room to absorb a split child, so one pass suffices.

    PROBLEM 3Core

    Explain why property 4 (all leaves at the same depth) means a B-tree's height can only grow at the root, never at a leaf.

    If a new level appeared underneath some leaf but not others, leaves would sit at different depths, violating property 4. So the only way to add a level without breaking that invariant is to add it uniformly at the top: when the root is full and needs to split, a brand-new root is created above it with the old root's median key, and the old root's two halves become its two children — every existing leaf just moved down by exactly one level simultaneously.

    PROBLEM 4Conceptual

    Why does making B-tree nodes larger (bigger t) reduce the number of disk accesses for a search, and why doesn't a similar trick help much for an in-memory binary search tree?

    Height of a B-tree is roughly logt(n) — increasing the branching factor t shrinks the height (and thus the number of node-reads = disk accesses) logarithmically. Since a disk access costs milliseconds regardless of how much of the page you read, packing many keys into the one page you already paid to fetch is essentially free extra work, and it directly cuts the number of expensive fetches.

    In main memory, the per-access cost is nanoseconds and roughly the same whether you touch 2 keys or 200 in one "node," so there's no analogous fixed cost to amortize — a plain binary tree (branching factor 2) with O(lg n) comparisons is already about as fast as comparison-based search gets, and widening nodes there mostly just adds more comparisons per node for no benefit.

    PROBLEM 5Challenge

    A B-tree of minimum degree t = 3 currently has height h = 2 (root, one internal level, leaves). What is the minimum possible number of keys stored in the tree?

    Minimize at every level: root has just 1 key → 2 children. Each of those (non-root, so ≥ t−1 = 2 keys) has the minimum 2 keys → 3 children each, so 6 leaves total. Each leaf (also non-root, min = 2 keys) holds 2 keys.

    Total = 1 (root) + 2×2 (internal level) + 6×2 (leaves) = 1 + 4 + 12 = 17 keys.

    05 / Minimum Spanning Trees

    Minimum Spanning Trees

    Given a connected, undirected, weighted graph G = (V,E), find a subset of edges T that connects all vertices at minimum total weight. Both classic algorithms are greedy, and both are proven correct by the same safe-edge theorem.

    Problem & Properties

    Find T ⊆ E such that (1) T connects all vertices (a spanning tree) and (2) w(T) = ∑ w(u,v) for (u,v)∈T is minimized. An MST has exactly |V| − 1 edges, has no cycles, and may not be unique (ties can produce different MSTs of equal weight).

    Kruskal's Algorithm

    Sort all edges by weight; scan in increasing order; add an edge if it connects two currently-different components (checked via a disjoint-set / union-find structure); skip it otherwise (would form a cycle).

    Time: O(E lg V) — dominated by the sort (or the union-find operations if edges are pre-sorted).

    Prim's Algorithm

    Grows a single tree from an arbitrary root r. At each step, adds the minimum-weight edge connecting the current tree to any vertex outside it (the "light edge"), using a min-priority queue keyed on each vertex's cheapest known connection.

    Time: O(E lg V) with a binary heap; O(E + V lg V) with a Fibonacci heap.

    Safe Edge Theorem

    Let A be a subset of some MST, (S, V−S) any cut that respects A (no edge of A crosses it), and (u,v) a light edge (minimum weight) crossing the cut. Then (u,v) is safe for A — i.e. A ∪ {(u,v)} is still a subset of some MST. Both Kruskal's and Prim's are instances of the Generic-MST pattern: repeatedly add a safe edge until A is a spanning tree.

    Generic MST algorithm

    GENERIC-MST(G, w)
1  A = ∅
2  while A does not form a spanning tree
3      find an edge (u,v) that is safe for A
4      A = A ∪ {(u,v)}
5  return A

    Loop invariant: A is always a subset of some MST. Trivially true at initialization (empty set). Maintained because only safe edges are added. At termination, A is a spanning tree that is also a subset of an MST — hence an MST itself.

    Finding a safe edge

    Let S ⊂ V be any proper subset that includes some vertex c but not vertex f, such that no edge of A crosses the cut (S, V−S) — i.e. (S, V−S) respects A. Among all edges crossing this cut, the minimum-weight one is a light edge. Intuitively: any MST must connect S to V−S with some edge, and swapping in a heavier crossing edge for a lighter one can only reduce total weight — so choosing the lightest crossing edge never costs you optimality.

    Proof sketch: Suppose the light edge (u,v) is not in some MST T that contains A. T must still connect S to V−S via some edge (x,y) on the unique path between u and v in T. Since (u,v) is a light edge, w(u,v) ≤ w(x,y). Swapping: remove (x,y) from T, add (u,v) — produces a new spanning tree T′ with w(T′) ≤ w(T), so T′ is also an MST, and it contains A ∪ {(u,v)}. Contradiction resolved: (u,v) is safe.

    Kruskal's — pseudocode

    MST-KRUSKAL(G, w)
1  A = ∅
2  for each vertex v in G.V
3      MAKE-SET(v)
4  create a single list of the edges in G.E, sorted into
5      monotonically increasing order by weight w
6  for each edge (u,v) taken from the sorted list in order
7      if FIND-SET(u) != FIND-SET(v)
8          A = A ∪ {(u,v)}
9          UNION(u,v)
10 return A

    Analysis: MAKE-SET calls: O(V). Sorting E: O(E lg E) = O(E lg V) (since E < V² ⇒ lg E = O(lg V)). The for-loop does O(E) FIND-SET/UNION calls; with union by rank + path compression these total O(E α(V)) ≈ O(E). Total: O(E lg V), dominated by the sort. (If edges arrive pre-sorted, it drops to nearly linear.)

    Prim's — pseudocode

    Uses a min-priority queue Q of vertices not yet in the tree, keyed by v.key = the minimum weight of any edge connecting v to the current tree A (∞ if none exists yet); v.π tracks v's parent in A.

    • Initialize: all keys ∞ except the root (key 0).
    • Repeatedly extract the min-key vertex u from Q, add edge (u, u.π) to the tree, then for each neighbor v of u still in Q, if w(u,v) < v.key, update v.key and v.π (a decrease-key).
    • Terminates when Q is empty — A = {(v, v.π) : v ∈ V − {r}} is the MST.

    Analysis (binary heap): Building/initializing Q: O(V). O(V) EXTRACT-MIN calls at O(lg V) each = O(V lg V). Up to O(E) DECREASE-KEY calls at O(lg V) each = O(E lg V). Total: O(E lg V). With a Fibonacci heap, DECREASE-KEY is O(1) amortized, dropping the total to O(E + V lg V).

    Kruskal's, worked

    Running Kruskal's on a sample weighted graph, processing edges in increasing weight order and testing each against the union-find structure:

    edge   decision
(c,f)  : safe   (different components -> add, union)
(g,i)  : safe
(e,f)  : safe
(c,e)  : reject  (c and e already connected -> would form a cycle)
(d,h)  : safe
(f,h)  : safe
(b,d)  : safe
(d,g)  : safe
(b,c)  : reject  (already connected)
(a,h)  : safe

    The algorithm stops once |V|−1 edges have been accepted (a full spanning tree); any edges considered afterward are irrelevant. Notice the rejects are exactly the edges whose endpoints Union-Find already reports as connected — adding them would close a cycle.

    Prim's, worked

    Starting from an arbitrary root r, Prim's grows one tree outward. At each step the priority queue holds every vertex not yet in the tree, keyed by its cheapest edge back into the tree; the algorithm repeatedly extracts the minimum (the current "light edge") and relaxes (decreases the key of) that vertex's neighbors still in the queue. Unlike Kruskal's, at every intermediate point the edges chosen so far always form a single connected tree (rather than a forest of pieces that merge later).

    PROBLEM 1Warm-up

    A connected graph has 12 vertices. How many edges must its MST contain? Can the MST contain a cycle?

    Edges: |V| − 1 = 11.

    Cycles: No — an MST is a tree by definition, and trees are acyclic. A cycle would mean at least one edge could be removed while keeping the graph connected, contradicting minimality (removing any positive-weight edge from a cycle only lowers total weight while preserving connectivity).

    PROBLEM 2Core

    Trace Kruskal's algorithm on these edges (already sorted by weight): (A,B,1), (C,D,2), (A,C,3), (B,D,4), (B,C,5) over vertices {A,B,C,D}. Which edges are accepted, and which are rejected?

    (A,B,1): different sets → accept. Union {A,B}.

    (C,D,2): different sets → accept. Union {C,D}.

    (A,C,3): {A,B} vs {C,D}, different → accept. Now all one component {A,B,C,D}. We have |V|−1 = 3 edges — done.

    (B,D,4) and (B,C,5) are never needed (algorithm can stop early), but if considered: both endpoints already connected → reject (would form a cycle).

    MST weight: 1 + 2 + 3 = 6.

    PROBLEM 3Core

    In Prim's algorithm, what does v.key represent at any point during execution, and what operation updates it when a new vertex u is added to the tree?

    v.key is the minimum weight of any edge connecting vertex v (currently outside the tree) to some vertex already inside the tree — i.e. the cheapest way v could currently join. It starts at ∞ for every non-root vertex.

    When u is extracted and added to the tree, for every neighbor v of u still in the queue: if w(u,v) < v.key, then a DECREASE-KEY sets v.key = w(u,v) and v.π = u — u is now v's cheapest known connection back to the tree.

    PROBLEM 4Conceptual

    Explain, using the safe-edge theorem, why Kruskal's algorithm is guaranteed to produce an MST rather than just some spanning tree.

    Every time Kruskal's accepts an edge (u,v), it's because u and v are in different components of the current forest A. Let S be the vertex set of u's component. Since u and v are in different components, no edge of A crosses the cut (S, V−S) — so this cut respects A. Because edges are processed in increasing weight order and (u,v) is the first crossing edge encountered (any earlier, lighter crossing edge would already have merged the two sides), (u,v) is a light edge for this cut. By the safe-edge theorem, a light edge for a cut that respects A is always safe to add. So every edge Kruskal's adds is provably safe, and Generic-MST's loop invariant (A ⊆ some MST) holds throughout — guaranteeing the final result is an MST, not just any spanning tree.

    PROBLEM 5Challenge

    A graph has all distinct edge weights. What does this guarantee about the number of MSTs the graph can have? What changes if some edge weights are equal?

    If all edge weights are distinct, the graph has a unique MST. Intuition: at every cut, there is exactly one light edge (no ties), and the safe-edge argument shows any MST must include every such uniquely-determined light edge for cuts respecting the edges chosen so far — leaving no freedom of choice at any step.

    With tied weights, multiple edges can be "equally light" across some cut, so different valid tie-breaking choices (different algorithms, or the same algorithm processing edges in a different order among equal weights) can yield different spanning trees — all with the same total weight, so all are valid MSTs. This is exactly the situation shown in the definitions: swapping one edge in a tied MST for another equal-weight edge produces a different MST of the same weight.
